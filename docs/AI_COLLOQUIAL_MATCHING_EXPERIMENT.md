## 3. 各版本做了什麼

### A：自動關鍵字權重＋去客套話（`TOWNPASS_KEYWORD_IDF=1`、`TOWNPASS_PAIR_MATCH=1`、`TOWNPASS_STRIP_FILLERS=1`）

- **關鍵字權重**（`registry.py`）：原本命中一個關鍵字的分數是「字數×3」。改成再乘上專有程度
  `(1+ln(頁數/用到這個詞的頁數)) / (1+ln 頁數)`：只有一頁用的詞 = 1，「申訴」（5 頁）0.72、「案件進度」0.72。
  只影響排序；「一句話裡有兩個需求」的判斷仍用原本的分數，所以不會因此拆錯。
- **字對比對**（`Registry.pair_matches`）：沒有任何關鍵字命中時，把每頁的詞拆成相鄰兩字（「古亭」「亭地」「地政」…），
  依同一個專有程度加權；句子涵蓋某個詞 60% 以上的資訊、至少 2 對、合計 ≥ 8.5 時列為候選（一律標 fuzzy，只能讓使用者確認）。
  「哪些」「服務」「問題」這種常見字對加起來到不了門檻。
- **去客套話**（`i18n.strip_fillers`，中、英、日、越、印尼、泰）：「我想要／幫我／請問／一下／那個／可以嗎」、
  「could you please / thanks」、「すみません／ください」、「làm ơn / nhé」、「tolong / dong」、「ช่วย / หน่อย / ครับ」等。
  只在模糊比對（讀音 fallback、拼字相近、字對、外語相近關鍵字）之前去掉；**精確關鍵字比對一律用原句**，不會少掉必要的詞。
  第一輪也在語意檢索前去掉，但在 dev 上沒有多找到任何正確頁面，反而讓「我想辦事情」列出「申辦服務」（dev 案例失敗），所以拿掉了。

### B：每頁的日常例句（`TOWNPASS_SEMANTIC_EXAMPLES=1`、`TOWNPASS_SEMANTIC_DIRECT=0.08`）

- `assets/assistant/capability_examples.json`：67 頁共 328 句（多數中文，少數英、日、越、印尼、泰），
  集中在最常失敗的頁面（災情表單、App 設定類、申辦表單、臨櫃各單位、圖書子頁）；最多的頁 8–15 句，有些頁只有 1–3 句。
- 語意檢索（`semantic.py`）把例句也算進去：每頁的分數取「目錄文字」和「例句」中最高的相似度。
  例句是「問句對問句」，相似度天生偏高，直接加進去會讓非服務句也拿到候選（dev 上 11 → 28/41），
  所以例句的相似度先減 0.05（`EXAMPLE_OFFSET`，在 dev 上掃 0–0.08 選出；非服務句回到 12/41，正確頁在候選中 183 → 215/252，留一法）。
- **明確時直接列候選**（`SEMANTIC_DIRECT`）：第一輪（只有例句）發現模型把 18 句裡 17 句正確、而且是唯一的候選拒絕掉
  （改成追問）。dev 上非服務句的領先分數最高 0.057，所以領先分數 ≥ 0.08 時不問模型、直接列候選讓使用者選
  （仍然只是候選，不會開頁）。report-only 集合裡這樣直接列的共 5 次，4 次正確、1 次列的是相近的「災情通報／土石流」，沒有一次發生在非服務句。
- 向量在啟動時算好並快取（與原本相同的快取機制，例句也在雜湊內，改了例句就會重算）。

### D：T2 第 2、3 項（`TOWNPASS_T2_GENERIC=1`）

- **未串接頁面不搶常用詞**：只命中一個未串接頁、而且只靠常用詞（兩個字的中文詞、一個外文字，或已串接頁也用到的詞，

  第一輪把「冊」整個算進去，讓「身心障礙手冊」進了圖書流程，已修正。

**開錯頁在每個集合、每個版本都和基線相同**（硬性條件成立）。開錯的那幾句都是精確關鍵字命中後模型選錯或關鍵字本身太寬
（「我要申請機車駕照」「低收入戶怎麼申請」→ 申辦服務、「公務人員訓練處…學費」→ 學雜費、堰塞湖說法 → 土石崩落），
三個版本都沒有碰到這一段；這要靠 T2 第 1 項（補／收窄關鍵字），不在本次範圍。

**模型的變動**：同一份基線程式重跑一次（base2），口語 100 是 53／8／38／1（第一次 54／8／37／1），其餘相同。
所以 ±1 句的差異不能當成版本的效果（A 的口語 −1 就是這一句「家門口那盞路燈壞了…」，關鍵字結果完全相同，是模型這次改成追問）。

**分數的一個假象**：報告 held-out 的「路燈不會亮」等 3 句，基線回「陳情表單預填：尚未串接」被評分程式算成「答對」
（訊息含期望頁的字），D 改成列出「路燈故障」表單，反而算成「確認」。所以 D 在這一集的答對 19 → 16 不是退步，實際上是變好。

### 各版本的影響在哪裡（report-only 集合）

- A：沒有可歸因的變化。關鍵字權重在全部 dev 句子中只改變 2 句的候選順序，沒有改變任何候選集合；
  字對比對大多找到語意檢索也會找到的頁面，還有 1 句（「中正區戶口登記那邊現在叫幾號」）先列了上層「臨櫃叫號」，擋掉語意檢索原本會給的「中正區戶政事務所」。
- B：口語 100 多 4 句列出正確候選（機車被偷 → 線上報案、折價券 → 優惠列表、換手機門號 → 基本資料、撥一九九九 → 1999）；
  外語 held-out 不變。報告 held-out 少 2 句：「對面公寓燒起來了」（建築物火災沒有例句，被別的火災表單的例句比下去後候選消失）、
  「有沒有什麼便宜的好康可以拿」（優惠沒有例句，改成列了 3 個不相關的候選，使用者要再說一次）。
- D：外語 held-out 2 句（日文、印尼文的路燈）從「未串接」改成列出路燈故障；報告 held-out 3 句中文路燈同樣。

## 5. 延遲與資源

- 語意層每次查詢（embedding＋計分，`metrics.semantic.ms`，report-only 與 dev 句子合計）：基線中位 19 ms／p95 42 ms，
  有例句 21／49–55 ms。純 Python 計分 799 段 5.5 ms → 1,127 段 7.8 ms（電腦，Python 3.13）；手機估計慢 3–5 倍，約 +10 ms。
- 第一次建索引多算 328 段：電腦約多 12 秒（背景、不擋請求），之後讀快取（約 1.7 MB，原本 1.2 MB）。手機未量，估計多 30–60 秒，只發生一次。
- 模型呼叫：B 的「直接列候選」省掉模型呼叫（新口語 dev 190 → 108 次），所以整體時間沒有變慢，部分集合反而略快。
  每輪秒數差異大多在 GPU 被其他評估共用的雜訊內。

## 6. 風險與限制

- **dev 的數字是樂觀的**：B 的例句有一半直接取自 dev 句子，dev 77 句「確認」大多是背過的句子；看 report-only 集合才準。
- **沒有例句的頁面會被擠掉**：例句越多的頁，越常排在前面。報告 held-out 少的 2 句就是這種情形。
  若採用 B，應該讓每個已串接頁都有幾句例句，而不是只補失敗最多的頁；補的時候不要從 held-out 或報告用的集合取句子。
- **直接列候選的門檻 0.08 只在 41 句非服務句上校正**；換 e5 模型、改目錄文字或大量增加例句後要重掃（`scratchpad/colloq/sem_sweep.py` 的作法）。
  它不會開頁，最壞情況是非服務句多出一個要使用者取消的選單。
- D 的「常用詞」判斷是規則：兩個中文字或一個外文字就算常用，可能讓少數本來直接回「未串接」的句子多一次模型呼叫（模型拒絕時仍回未串接）。
  B＋D 在 dev 上有 1 句變差：「有沒有問卷可以填」原本直接回「意見調查：尚未串接」，改成列出「常見問答、繳費查詢、意見調查」
  （語意排第一的是已串接的常見問答）。若採用 D，可考慮要求語意第一名的分數明顯領先，或把「問卷」這類詞列為不需讓出的詞。
- B＋D 與 C＋D 的結果完全相同（A 沒有額外效果）。B＋D 那一輪的秒數較高，是同時段 GPU 被其他評估占用，模型呼叫次數幾乎相同（外語 held-out 120 → 122 次）。
- 評估中模型會有 ±1 句的變動（見上）；樣本小（新 held-out 80 句、27 個功能），結論只到「沒有退步、B 在沒看過的口語句有小幅進步」。
- 手機上沒有驗證（e5 計分、例句索引建置時間）。
