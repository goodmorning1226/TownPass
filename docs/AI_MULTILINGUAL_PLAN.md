# 多國語言規劃（V7）：Whisper 版與 no-Whisper 版

狀態：2026-11-07 規劃，尚未實作。本文件取代 `AI_VOICE_UI_PLAN.md` 第 6 節中「外語先翻成中文再走原流程」的做法，原因見第 2 節。
目前 App 本身沒有多語系架構（只有 `intl` 套件），各服務頁面（TownPass-Services 網頁、原生頁）也不在本 repo。

## 1. 範圍

| 會做 | 不做（不在本 repo 或另案） |
| --- | --- |
| 助理介面：全螢幕面板、提示、按鈕、錯誤訊息 | 整個 App 介面翻譯 |
| 語音輸入：選定語言的辨識 | 服務頁面本身（WebView 網頁、原生頁）的翻譯 |
| 助理理解：外語請求能找到正確服務 | 書名翻譯（示範書目只有中文書名） |
| 助理回覆：文字與朗讀都用選定語言 | 台語（另見 V8） |

## 2. 理解：功能清單加外語關鍵字（不另做翻譯）

- 決策模型 Ministral 3B 本身是多語模型，看得懂英文、日文等請求。看不懂外語的是前面的檢索：`registry.search` 依中文名稱與關鍵字比對，外語請求會找不到候選。
- 原規劃是「先用 Ministral 翻成中文」。在手機上，這要多呼叫一次模型，每句多約 5–8 秒（實測決策一次約 7 秒），翻譯也可能把服務名稱或書名翻錯。
- 新做法：
  - `capabilities.json` 每個功能加上 `keywords_<lang>` 與 `title_<lang>`（例如 `keywords_en: ["water bill", "pay water"]`）。
  - `registry.search(text, lang)` 同時比對中文與該語言的詞。
  - 決策 prompt 不變：證據裡的 `original_text` 就是外語原文，候選的 `title` 仍是中文。
  - 每個請求還是只呼叫模型一次。
- 規則中寫死中文的部分（取消、問候、「有哪些功能」、否定詞、「第 N 個」）改為依語言查表，每種語言各一份。
- 讀音修正只用於中文。英文等拼音文字改用現有的字形相似度（`difflib`）處理拼錯的字。
- 回覆：後端的固定回覆改成「訊息代碼＋參數」，依語言套用文案。服務名稱顯示 `title_<lang>`，沒有時顯示中文。

## 3. 語音辨識

| | Whisper 版 | no-Whisper 版（手機內建辨識） |
| --- | --- | --- |
| 中文 | Breeze-ASR-25（或消融實驗選出的模型） | Google 裝置端 `cmn-Hant-TW` |
| 其他語言 | OpenAI 多語 Whisper，型號依消融結果決定（large-v3-turbo、small…），用 `-l <lang>` 指定語言，不自動偵測 | 同一個辨識器換語言標籤（`en-US`、`ja-JP`…），語言包第一次使用時下載，有進度條 |
| 記憶體 | 一個多語模型可以同時涵蓋中文與外語；如果中文仍要用 Breeze，就要兩個模型，可以只載入目前選定語言的那一個 | 不占 App 記憶體 |
| 關鍵字提示 | 依語言組 vocabulary prompt | 依語言組 biasing 詞 |

語言由使用者在語音列左下角的選單選擇，預設值見第 4 節。不使用自動偵測：短句的自動偵測容易錯，而且會多花時間。

## 4. 介面與朗讀

- **語言選單**：語音列左下角（目前保留的空位）。
  - 只列出這次支援的語言。no-Whisper 版另外標示語言包是否已下載。
  - 選擇會記住。預設值是 App 的語言設定；App 目前沒有語言設定，所以預設為中文。
- **介面文字**：助理介面約 40–60 句文字，改用 Flutter 的 `intl` ARB 檔。只翻助理介面，不動 App 其他頁面。
- **朗讀**：`flutter_tts` 依選定語言設定語音。手機沒有該語言的語音時，只顯示文字，並提示使用者到設定下載語音資料。
- **開啟服務頁面時**：提示「此頁面為中文」，因為服務頁面本身不會翻譯。

## 5. 契約（向後相容）

- `/v1/assistant/turns` 與 `/v1/assistant/transcriptions` 新增選填欄位 `language`（BCP-47，例如 `zh-TW`、`en`）。沒有帶時視為 `zh-TW`，舊版 App 不受影響。
- 回應新增 `language` 欄位，表示回覆所用的語言。
- `capabilities.json` 的 `version` 加 1，並同步更新 App 與後端。

## 6. 評估

- **文字**：把 `evaluate.py` 的 dev 與 held-out 題目翻成目標語言，另外建一組 `eval_<lang>.py`，用相同的分類計分。翻譯版的 held-out 一樣不拿來調整。
- **語音**：沿用 `eval_asr.py`。合成語音只用來檢查流程是否能跑；Windows 目前只有 zh-TW 與 en-US 語音，其他語言要另外安裝。準確度以真人錄音為準。
- **門檻**：錯誤服務與意外導航維持 0；正確率與中文版的差距要記錄下來。

## 7. 階段

1. **基礎建設＋英文**，兩個版本都做：
   - 語言欄位與選單。
   - 功能清單英文名稱與關鍵字。
   - 規則表與回覆文案。
   - ARB 介面文字。
   - 英文辨識（Whisper 多語模型、Google `en-US`）與英文朗讀。
   - 英文評估集。
2. **第二、三種語言**（使用者選定後）：只需要補該語言的關鍵字、規則表、文案、評估集。
3. **視消融結果調整**：如果單一多語 Whisper 模型的中文也夠準，Whisper 版就改成一個模型涵蓋所有語言，減少記憶體。

## 8. 使用者決定（2026-11-07）

1. **語言**：英文、日文（觀光客）、越南文、印尼文、泰文（新住民與移工），共 5 種。
2. **外語關鍵字與文案**：由我先擬，再請熟悉該語言的人校對。
3. **Whisper 版中文**：等語音消融結果出來再決定。
4. **服務頁面的語言**：跳轉後，頁面本身與頁面上的指引也要換成使用者說的語言（見第 10 節）。

## 9. 語言判定層

使用者不必先選語言；選單保留，作為手動指定或修正。

| 輸入 | 怎麼判定 | 模型 | 每次大約花費 |
| --- | --- | --- | --- |
| 打字 | 文字系統：假名→日文、泰文字母→泰文、越南文聲調字母→越南文、漢字→中文；只有拉丁字母時（英文或印尼文），用常見詞表判斷 | 不需要模型（規則與詞表） | 小於 1 毫秒 |
| 語音，Whisper 版 | Whisper 本身的語言偵測：看編碼結果後的第一個解碼步驟 | 多語 Whisper（turbo、small 等）不必另外加模型；Breeze 只認得中文與英文，所以要先用 Whisper tiny 或 base 判定 | 用多語模型時約多一次解碼（數十到數百毫秒）；另外跑 tiny 大約多 0.3–1 秒，以消融實驗實測為準 |
| 語音，no-Whisper 版 | 系統辨識器必須事先指定語言，不能事後判定 | 先用 Whisper tiny 判定語言（約 30 MB），再用該語言啟動系統辨識；App 錄的同一段音訊可以重用 | 約多 0.3–1 秒（待測） |

- 信心不足時，沿用上一次判定或選單中的語言，不會猜。
- 短句（一兩個字）的語言判定容易錯，所以優先沿用使用者上一句的語言。
- 判定結果會顯示在語言選單上，使用者一眼就知道目前用哪種語言，也可以手動改。

## 10. 跳轉後的頁面與指引

| 內容 | 做法 | 備註 |
| --- | --- | --- |
| 助理回覆、角落提示、之後的任務引導文字 | 本 repo 的文案，依語言套用 | 品質由人工校對控制 |
| 原生頁面（`lib/page/*`，在本 repo） | 改用 ARB 多語系；這等於整個 App 的國際化，工作量最大 | 可以先做助理最常開啟的頁面 |
| WebView 服務頁（TownPass-Services，不在本 repo） | App 在頁面載入後透過 JS 取出可見文字，用裝置端翻譯模型翻好再寫回頁面；原文保留，可以切回 | 不修改網頁原始碼；表單送出的值不翻譯 |

- **裝置端翻譯模型**：建議 Google ML Kit Translation。
  - 每種語言約 30 MB，可離線，免費，支援英、日、越、印尼、泰文。
  - 每句約數十毫秒，一頁大約 0.5–2 秒（待實測）。
  - 中文來源對繁體字的品質需要實測。
- **不用 Ministral 翻譯頁面**：每段要好幾秒，一整頁要數十秒，太慢。
- **限制**：翻譯模型可能翻錯專有名詞（機關名稱、費用項目）。這些專有名詞改用功能清單中審核過的外語名稱。
